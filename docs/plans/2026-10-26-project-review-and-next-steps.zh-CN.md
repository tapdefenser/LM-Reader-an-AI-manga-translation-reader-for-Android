## 2. 新确认的问题与直接证据

### A. 当前主分支 CI 在本地化阶段失败

**事实：** [GitHub Actions run 39953954550](https://github.com/tapdefenser/LM-Reader-an-AI-manga-translation-reader-for-Android/actions/runs/39953954550) 对应当前 HEAD，结论为 failure。SDK、模型和源码准备通过，`Check localization` 失败；随后的构建、测试、Lint 和 APK 上传均被跳过。

本地运行 `python tools/test_ui_translations.py` 得到同样结果：6 项中 1 项失败，`test_catalog_has_all_current_localizable_literals` 检出 **240 条中文模板未进入英文目录**，这 240 条也都没有对应的人工 overrides。这里统计的是模板，不是 240 个页面或必然可见的控件。

缺口主要分布在：

| 文件 | 缺失模板涉及数量 |
|---|---:|
| `VideoTranslationOptionsDialog.kt` | 50 |
| `MediaTaskBackup.kt` | 21 |

| `VideoResultImports.kt` | 16 |

同一模板可能出现在多个文件，表中数字不用于相加得出总数。英文界面的现有翻译器会尝试模板/片段替换，缺失完整条目可能产生残留中文或混合文案；不能把所有缺项都声称为已经观察到的页面问题。

**下一步：** 先修正下面 B 中的错误原文，再补齐人工 overrides 与实际打包的 `app/src/main/assets/i18n/zh_en.json`，保留占位符并检查关键英文页面。恢复 6 项检查后，让完整 CI 实际运行到结束；不能预设后续原生构建和 Lint 一定通过。

### B. ASR“自动”模式的说明与执行不一致，手动 GPU 风险仍存在

**静态确认：**

- [ASR 设置页](../../app/src/main/java/com/lmreader/ui/settings/asr/LocalAsrScreen.kt#L237)仍显示“自动优先真实 GPU，初始化失败才回退 CPU”。
- [AsrBackend.AUTO](../../core/translation/src/main/java/com/lmreader/core/translation/asr/AsrBackend.kt#L20)的描述仍是优先 Vulkan、其次 OpenCL；下拉菜单直接使用这份描述。
- [native 实现](../../core/translation/src/main/cpp/asr_backend.cpp#L535)已经将 AUTO 固定为 CPU，设置页下方的状态摘要也说明默认 CPU。同一个页面因此存在相反说明。
- 手动 Vulkan/OpenCL 仍可选择。此前已在目标 Adreno 手机上记录 Vulkan 推理导致进程级 native 崩溃，最新线上 Release 也明确披露此问题；本轮没有再次触发崩溃，也没有把一台设备的结果推广到全部 GPU。

**下一步：** 统一原文、枚举说明和中英文目录，明确“自动使用 CPU”。对已知崩溃的设备/驱动组合提供明确的不可用处理或实验入口限制，避免普通使用者直接进入已知危险路径。GPU 根因定位单独立项；进一步试验应采用能隔离崩溃并取得诊断信息的方式，先完成 CPU 路线的真实质量和性能记录。

### C. “补齐翻译能力”可能打开错误设置页

**静态确认：** [resolveTaskOptions](../../app/src/main/java/com/lmreader/ui/navigation/LmReaderNavHost.kt#L46)对所有 `CAPABILITY` / `API_ACCESS` 问题，只根据任务 `options.subtitleSource == ASR_LOCAL` 判断是否打开 ASR 设置。视频任务快照默认并固定使用 `ASR_LOCAL`；它不表示本次错误来自 ASR。

因此，视频画面/字幕工作流缺机翻包或 API 配置时，按钮也可能把用户带到 ASR 设置，无法直接解决当前问题。这条结论来自确定的路由条件和任务快照；本轮没有做设备点击复现。

目前已有按节点检查 API/本地机翻、`TaskWaiting`、队列补齐按钮和设置跳转，不能把 1.5 重新描述成完全没有实现。

**下一步：** 为等待原因补充具体能力/节点信息，至少区分 ASR 模型、机翻语言方向、SEG/OCR、API 配置与原文件授权。按真实缺项导航；返回后重新检查并允许继续原任务，保留原快照和人工成果保护。无法满足原快照时明确要求更新选项，不悄悄替换配置或重新发送请求。

### D. 视频库查询分页尚未贯通到显示层

**静态确认：** [VideoCatalogDao.observeEntries](../../core/database/src/main/java/com/lmreader/core/database/media/VideoCatalogDao.kt#L24)读取全部视频行；[VideoCatalogScreen](../../app/src/main/java/com/lmreader/ui/video/catalog/VideoCatalogScreen.kt#L52)观察完整集合，再在后台线程过滤和排序。MediaStore 扫描分页已经实现，但不等同于数据库列表分页。

**下一步：** 在有较大媒体库时记录首屏、搜索/排序耗时和内存，再把筛选/排序/分页下推数据库。保留稳定排序、未知值末尾、书架状态、滚动恢复及点击时播放列表快照。当前仅确认结构性扩展限制，没有实测证明小库已卡顿，不把它列为首个阻断。

## 4. 建议的执行顺序与验收门槛

### 第一轮：恢复可验证的版本基线

1. 修正 B 的 ASR 原文和状态语义，再完成 A 的 240 条目录缺口。先检查中文，再检查关键英文页面，避免把错误说明翻译后继续保留。
2. 修复 C 的能力补齐导航，复用现有等待任务与返回路径；先以“视频画面缺机翻包”和“缺 API 配置”做最小纵向样本。
3. 同步 README 中英构建步骤、当前视频使用说明和总进度入口。
4. 运行受影响检查，通过后执行一次完整 CI，保存真实结果；如果出现下一个失败，按日志继续修复。

**交付门槛：** 本地化 6 项通过；AUTO 在设置、枚举、实际后端中的含义一致；缺机翻/API/ASR 能分别到正确入口并回到原任务；CI 实际跑过构建、测试、Lint、JNI 而非停在前置步骤。沿用原证书和已有数据格式；整改不自动意味着发布新 Release。

### 第二轮：完成一次有边界的视频 ARM 验收

先固定视频、语言、工作流、模型和 CPU 后端，复用当前手机自测矩阵。按顺序进行：

| 场景 | 必须确认的结果 |
|---|---|
| 30–60 秒片段，画面/字幕/两者三种模式 | 对应分支运行、逐步有成果、实际后端为 CPU；记录耗时与明显识别/时间轴问题 |
| 新建任务，调整采样间隔、截图长边、识别上下边界 | 新任务按新选项执行，旧任务维持快照；区域坐标和显示范围正确 |
| 气泡持续、文字替换、切镜头及快速跳转 | 轨道在有效时间显示，变化后结束；旧请求不能污染新时间位置 |
| 横竖屏编辑、保存并退出重进 | 画面适配、工具栏可用，气泡和字幕修改持久化，迟到结果不覆盖人工成果 |
| 离开播放器/锁屏后继续，再暂停/取消 | 后台按既定规则推进，已完成成果可用，资源最终释放 |
| 进程结束后重新进入 | 队列按当前约定默认暂停，用户明确继续；不重复已确认成果或不明远端请求 |
| 上述短链通过后再跑一个较长样本 | 记录分阶段内存/耗时、任务进度、取消释放和系统中断；检验是否随处理时长持续增长 |

**交付门槛：** 形成设备、Android、模型、配置、样本时长、结果和缺陷的固定记录。出现问题只补受影响回归；没有必要每次重新打包和重复全部测试。真实云提供方另列有成本的验收项，不混入默认本地流程。
