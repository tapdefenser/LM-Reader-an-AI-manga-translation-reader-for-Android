## 一、产品方向和已经确定的边界

应用围绕一条主线组织：**导入外语内容 → 通过工作流看懂 → 校对并保存成果 → 继续阅读/观看或分享。** 阅读器、视频、扩展和 Agent 共用工作流、任务及成果，避免各做一套。

当前最需要解决的是这条主线的可靠性：块能否正确连接、用户能否理解不可选的原因、成果能否保留，以及重译或清理会不会伤及人工修改。近期一边补齐这些问题，一边交付本地视频。

以下决定固定下来：

- **名称保持 LM-Reader。** 本阶段不安排品牌、显示名、包名和签名变更。
- **近期重点是阅读、翻译巩固和本地视频；新增大功能中视频优先于 Agent。** 不以完整插件系统或跨平台迁移作为视频开工条件。
- **视频仅接入本地文件。** 不建设站点下载、外链抓取或搬运服务。
- **视频画面翻译与音频字幕分别建设。** 画面复用现有图像工作流，音频先形成带时间的文字，再进入文本翻译工作流。
- **播放原视频，加遮罩和字幕。** 保存翻译数据，本阶段不生成、烧录或重新编码新视频。为识别而解码音轨、取帧仍属于必要处理。
- **不内置通用聊天大模型推理引擎。** 不安排 llama.cpp、聊天模型下载或相关基准项目；专用离线 ASR 属于视频语音识别能力，保留评估和集成。
- **扩展的核心是新增猫爪块。** 新块可以接入新引擎、实现新的 API 调用规则或新的处理逻辑；也允许把已有流程封装成组合块。扩展设计必须支持真正新增能力。
- **Agent 不以配置 API 为启用条件。** 无 API 时，用户仍能在 Agent 入口选择内容和已有工作流，执行可用的本地翻译。自由对话、模型规划和生成式摘要另按模型能力启用。
- **远期优先 iOS。** 近期做好 Android，并让新增协议和成果格式便于移植；其他平台排在 iOS 验证之后。
- **GitHub 用户规模统计与提交管道是近期必做事项。** 统计采用明确的去重安装/活跃口径，汇总到 GitHub，不以下载次数替代；提交管道同时包含搭建和简化优化。
- **GitHub JSON + Gitee 镜像用于只读分发。** 用户成果先保存在本地；统计通过独立接收接口汇总后发布，静态 JSON 不直接承担客户端上报或在线分享服务。

## 二、应用入口怎样组织

近期首页优先提供“继续阅读”“继续观看”和“导入内容”。保留图库与书架，视频库放在图库下方；视频收藏、片单承担视频版书架的用途，引用同一个视频条目，不复制视频文件。

工作流入口集中管理猫爪和预设；任务入口集中显示漫画、视频和未来 Agent 发起的任务。设置中提供“数据与空间”。相关入口可以复用现有导航，不要求先重做整个应用界面。

Agent 阶段再增加会话式任务入口，并支持从阅读器/播放器唤起。宽屏可在右侧收纳历史，手机使用抽屉或独立历史页，避免左右栏挤占内容。首版 Agent 仍要能回到原页面、原视频时间段和已完成成果。

## 三、执行顺序

下表表示交付顺序，不是每个对话都要把一整批做完。每个编号任务均可单独接续；先完成确认的阻断，再开展后续工作，不要求第一批重写全部猫爪。

| 批次 | 用户得到什么 | 优先级与依赖 |
|---|---|---|
| 第一批：猫爪与成果可靠性 | 上下文、列表合并等规则清楚，已有成果得到保护 | 立即开始，只处理确认问题和必要基础 |
| 第二批：阅读体验与视频入口 | 设置更简单、本页能分享、本地视频可播放并接入翻译帧 | 近期；视频适配与独立阅读改进可分开推进 |
| 第三批：可持续使用的视频画面翻译 | 连续播放遮罩、字幕导入、保存并继续观看 | 近期，接第二批视频适配 |
| 第四批：视频声音与完整资源管理 | 离线 ASR、语音 API 路线、可理解的数据清理 | 近期；ASR 评估从第二批开始 |
| 第五批：扩展和工作流分类 | 新引擎、新 API 规则、新猫爪块可以规范接入 | 阅读与视频基本可用后；必要接口随前面批次提炼 |
| 第六批：Agent | 无 API 也能通过会话任务入口执行已有工作流 | 复用前面的任务、能力检查和成果系统 |
| 第七批：iOS | 在优先的第二平台上跑通真实阅读与视频链路 | 远期；近期持续避免新增平台绑定 |

GitHub 用户统计、提交/发布管道搭建与优化、只读目录分发是三项独立配套任务。前两项明确列为近期必做，在第一、第二批期间启动并单独验收，不等待 Agent 或 iOS，也不作为视频开工前置条件。统计尚未部署时记录为未完成，不能以下载徽章替代交付。

## 四、第一批：猫爪与成果可靠性

### 1.1 修复“新增上下文的输出不可选”

先构造最小工作流，核对用户报告对应的操作路径。已知代码允许 CONTEXT 类型，但只显示可写变量；异步分支中的外层上下文会被过滤，未声明或声明在后也没有候选。校验器和执行器同样禁止这一父层写入。

实施内容：

- 输出明确标成“写入上下文”，显示需要的类型，解释选择的是已有变量。
- 没有可用变量时提供创建入口或直接可操作的创建指引；新建变量放在该步骤之前的合适作用域。
- 对外层异步只读、循环条目、声明顺序和搜索不匹配分别提示原因，避免只显示“无匹配变量”。
- 编辑、保存校验与运行采用同一可写规则。首轮保留明确的同步积累语义，不直接开放并行分支写同一个上下文。
- 若必须跨并行项积累，使用有序结果收集后构造上下文；需要新增共享追加语义时另立任务，同时解决顺序、丢失更新和旧流程兼容。

完成标准：同层声明后可写，外层同步可写，外层异步有明确限制及解决路径；保存重开后行为相同。不能以“界面能选但运行报错”通过验收。

### 1.2 统一“合并列表”的输入输出

编辑器目前只允许列表，新建默认却可能选择文本，校验和执行又接受文本拼接。统一为“同类型列表合并到列表”；普通文本拼接继续使用对应文本追加能力。

新建时选择兼容列表；没有目标时提示创建，不生成一个表面可运行的错误默认值。检查旧工作流和队列快照中是否存在用此块拼接文本的情况；有则提供等价迁移或清楚的兼容处理，避免静默改变结果。

完成标准：新建、编辑、导入、保存重开和运行的类型一致；覆盖嵌套和异步父层列表，保留现有并发安全约束。

### 1.3 把 21 种块的检查落实成可用行为

以检查附录为清单，逐项核对当前版本的默认输入、输出目标、空值、作用域和实际副作用。第一批只修复确认的冲突和影响任务的说明，剩余问题记录后分批处理。

重点包括：SEG 会替换本页区域并清空旧记录；每项循环可能回写原列表；按顺序回填要求从 1 开始的整数；流式 API 的“完整条目”与网络分片不同；不同宿主是否支持整作品单请求必须明确。

保留 PREPARE_MANGA、RETURN 等旧格式兼容路径，不重新作为常用新建块开放。不把缺少引擎选择器误判为本地机翻不能运行；当前缺省引擎已有处理。

完成标准：形成“已修复／已复核无需改／后续处理”的清单；界面展示的可连接关系与校验、执行相符。优先复用已有测试，仅为真实差异补充回归案例。

### 1.4 保护已有译文和人工校对

沿用现有页成果的源文件校验、版本冲突和原子保存，补足任务与成果匹配规则。至少记录或比较源内容、源/目标语言、影响语义的工作流版本与必要引擎配置；纯显示样式变化不触发识别重跑。

旧成果可以继续查看。配置变化后，旧成果不能默默计入新任务的完成结果；对旧数据缺少的字段按兼容状态处理，不推断为已匹配。人工校对被识别为正式成果，重译前明确覆盖范围，后台迟到结果不能覆盖更新的人工版本。

批量导出在创建任务时捕获配置，重试和恢复使用同一快照；本页分享在点击时捕获当前显示效果。先核对现有实现，仅补缺口，不重写整个成果数据库。

完成标准：换目标语言、换工作流、校对后重译、取消后迟到、导出后改样式和任务恢复都有确定行为；不自动发起新的付费请求。

### 1.5 能力检查和首次使用

在任务开始前说明当前工作流缺少哪个模型、语言方向或 API 能力，提供补齐并继续原任务的路径。简易配置只暴露必要项；高级 API 覆盖保留明确作用域，不能把所有识别/翻译节点按一个配置盲目替换。

此处能力检查成为后续视频和 Agent 的共同入口。工作流确实使用 API 时才要求对应配置；纯本地工作流无需 API。

**第一批的交付：** 确认问题的代码修复、必要回归、已更新的猫爪问题清单和实施记录。既有未提交的引擎迁移不自动算本批成果，也不回滚。

## 五、第二批：阅读更顺手，本地视频开始接入

### 2.1 翻译设置分层折叠

默认显示源/目标语言、工作流或翻译方式、开始操作及准备状态。识别、排版、性能与 API 等高级选项按用途分组折叠，摘要展示当前关键值，展开后可编辑；不要把错误和缺包提示藏进折叠区域。

完成标准：常用翻译无需逐项理解全部参数；修改高级设置能够正确保存，原有可调能力仍能找到。覆盖中文与英文界面的基本可读性。

### 2.2 阅读器分享本页和保存本页

提供原图、当前译文效果两种输出。使用整页图像与渲染结果，不截取工具栏或当前可见的一小段。保存到用户选择的文件位置或相册；分享交给系统分享面板。

点击时捕获页、成果版本和显示样式；存在未保存校对时走现有草稿处理规则，明确采用哪个版本。分享临时文件授予必要读取权限并按生命周期清理，不能在接收方尚未读取时删除。图片较大时控制内存，失败有可重试提示。

完成标准：其他应用能打开完整输出；原文件保持完整；无译文、长页、大图、未保存校对及保存失败有清楚行为。

### 2.3 本地视频导入、播放与帧适配

新增本地视频条目，保存稳定身份、文件引用、基本媒体信息及观看位置。能保持授权时引用原文件；确需复制时明确告知。文件被移动或授权失效时支持重新定位，不把它误判成需要重新翻译的另一部作品。

建立播放器与取帧适配，把帧转换为现有图像工作流能接收的临时输入。隔离视频会话与漫画页面身份，防止结果串写。复用 SEG、OCR、机翻/API、区域轮廓和可复用的视频匹配逻辑；新增时间戳、旋转/缩放坐标、取消和任务归属。

分析图像可以缩小，成果坐标必须映射回原视频。现有页成果约四百万分析像素的限制不能直接用来保存 4K 全帧；不长期保留每一帧原图。

完成标准：导入并播放本地视频，暂停取帧，选择现有图像流程，得到位置正确的译文遮罩；切换文件或跳转后旧任务不能盖到新画面。**这只是内部里程碑，第三批完成前不宣称视频翻译已交付。**

### 2.4 提前开展离线 ASR 评估

使用少量固定音频样本比较专用组件，候选为 [whisper.cpp](https://github.com/ggml-org/whisper.cpp) 与 [sherpa-onnx](https://github.com/k2-fsa/sherpa-onnx)。先比较，再选一个集成，不同时嵌入两套生产运行时。

报告包含：候选组件及模型版本、支持语言、时间戳能力、下载体积、峰值内存、识别质量、处理时长、取消和释放表现，以及未来 iOS 接入依据。Android ARM 真机数据与模拟器结果分开记录，不预设必须使用 GPU，也不把上游支持平台等同于本应用已经跑通。

完成标准：给出有实测依据的选择或尚未达标的具体原因。缺少真机或模型时明确记录未验证项，不用虚构的性能结论代替。

### 2.5 新数据必须先登记

从视频第一份数据起，就区分原媒体、正式译文、字幕、模型和中间缓存。记录归属、占用、是否可重建、任务是否仍在使用；后续资源管理在此基础上接界面。

**第二批的交付：** 可独立验收的设置改进、本页分享/保存、本地播放器与单帧适配、ASR 评估报告。它们可以分别完成和发布。

## 六、第三批：交付可持续使用的视频画面翻译

### 3.1 连续播放、跳转与遮罩

按内容变化和已有结果决定何时分析，限制解码与翻译并发，避开无限排队。复用现有去重和区域匹配时核对输入条件；明确每份结果的原始播放时间及有效区间。

区分三种显示内容：

- 气泡：保留轮廓，在对应区域遮盖原文并排译文。
- 游离文字和画面硬字幕：按画面位置显示，不强套气泡形状。
- 音频生成或导入字幕：独立时间轨，与画面遮罩分别开关。

处理拖动、快速连续跳转、暂停、倍速、旋转、黑边和显示缩放。旧请求完成后只回到它所属的帧/时间段，不能按“当前播放位置”直接贴上去。画面变化或结果过期时移除不可靠遮罩；确实来不及翻译时显示处理中状态。

### 3.2 已有字幕导入与翻译

先支持 SRT，保留条目身份、起止时间、原文与译文，按需要再增加其他格式。处理常见 UTF-8/BOM、换行、时间格式、空文件、越界和重叠条目；非法内容指出位置，不能静默错配。

字幕走文本翻译流程。按场景调整入口和校验，不强制带漫画、章节、页面和 SEG，也不靠假图片绕过。翻译可以带邻近文本作为上下文，输出仍按稳定条目映射，不能改变时间关系或依赖并行追加的完成顺序。

提供原文、译文、双语显示，以及基本文字校对和字幕偏移调整；支持导出译文/双语 SRT 并通过系统分享。未配置 API 时，已就绪且支持相应语言方向的本地机翻可以执行。

### 3.3 保存结果、进度和视频书架

把画面区域及译文按时间保存，字幕按独立轨保存；不改原视频。保存原媒体身份、任务配置、成果版本、人工修改和观看进度。退出再打开时复用匹配结果；源文件变化或身份不匹配时提示重新绑定/重算。

视频库显示继续观看和翻译状态；片单/收藏引用同一条目。作品详情先提供成果及可归属缓存的占用，支持停止任务后清理可重建缓存，保护正在使用的数据。完整回收站与全局清理在第四批补齐。

**第三批的完成标准：** 本地视频导入 → 连续播放遮罩 → 拖动/旋转/倍速 → 导入字幕并翻译/校对 → 关闭再打开仍能继续。原视频没有被重新编码，字幕和遮罩可独立控制。用连续播放验收，不能只展示暂停截图。

## 七、第四批：视频声音与完整资源管理

### 4.1 集成选定的专用离线 ASR

依据第二批报告选择一套组件及首批模型，按需安装并展示体积、语言与准备状态。接入音轨读取、解码、必要分段和音频引用；将识别结果映射为原视频时间轴上的字幕条目。

分段要处理重叠、重复文字、边界漏字与时间偏移；无声、音乐和识别不确定时避免编造内容。长视频分段保存进度，支持取消、重试和释放模型，不要求整个视频一次进入内存。

把“语音识别”作为明确的工作流能力接入，复用已有文本翻译步骤和字幕成果。首版可以后台分段生成字幕，实时识别和逐词效果根据实测再安排，不承诺所有设备实时运行。

完成标准：在记录清楚设备与模型的条件下，跑通本地视频音轨 → 离线识别 → 本地或 API 翻译 → 播放/校对/恢复；记录识别质量、字幕时间偏差、处理时长和资源占用。

### 4.2 支持语音识别 LLM API

在离线 ASR 评估路线之后接入一个实际可用的提供方，作为可选能力。声明它接受的音频格式、时长、请求方式、结果结构、时间戳、错误和取消语义。复用 API 调度与配置，按需要扩展真实音频附件能力。

有原始时间戳则保留；只有文本的服务不能直接冒充已完成字幕对齐。需要补对齐能力时独立实现并验收；在此之前限制在它确实能完成的任务。仅支持文字或图片的配置不能被标记成支持音频。

完成标准：请求结果能可靠落到原视频时间轴；能识别不支持的配置、取消与失败重试，密钥不写入导出成果或日志。无此 API 时，本地与字幕导入路径继续可用。

### 4.3 完整的数据与空间入口

全局设置提供“数据与空间”，作品详情提供“这部作品的数据”。作品统计只含可归属的数据，共享模型与应用运行缓存单列，避免重复计算和误删依赖。

| 数据 | 默认管理规则 |
|---|---|
| 原图、原视频及用户主动保存的文件 | 清缓存不删除；移除库条目与删除原文件分成不同操作 |
| 译文、校对、字幕和批注 | 正式成果，支持备份及明确范围的删除；用户成果删除可进入回收站 |
| 缩略图、分析帧、音频中间文件 | 标明可重建，按预算清理；正在使用或恢复所需的数据受保护 |
| 模型文件 | 单独卸载，说明影响的能力；删除作品不连带卸载共享模型 |
| 已加载模型及引擎内存 | 使用“释放运行资源”，与删除磁盘文件区分 |
| 失败/完成任务临时数据与日志 | 按任务状态和保留规则清理，保留恢复必需的部分 |

按页、章节、视频时间段或整部作品管理成果。回收站支持恢复和明确的保留/容量规则，先验算占用与依赖再删除；它只管理应用负责的数据，不接管外部原文件。共享缓存可能无法归属单部作品时，在全局说明，不虚构精确归属。

完成标准：清缓存后人工成果仍在、活动任务不损坏、模型仍可被其他作品使用；删除和恢复的范围可预期。复用现有备份回滚和恢复机制，补入视频与字幕数据，不另外建立平行备份体系。

**第四批的交付：** 离线语音识别、可选语音 API、完整资源管理分别作为独立交付点。字幕导入不等待 ASR 选型，已经完成的画面视频功能不等待语音 API。

## 八、第五批：扩展首先服务于新增能力

### 5.1 明确三种扩展方式

| 方式 | 能新增什么 | 接入方式 |
|---|---|---|
| 引擎适配块 | 新的 SEG、OCR、翻译、ASR 或其他处理引擎 | 将引擎适配器注册为猫爪能力，声明输入输出及资源生命周期；可调用用户已配置的本地服务，原生引擎需要对应平台实现 |
| API 规则块 | 不同于现有协议的请求、认证、附件和返回解析规则 | 用户/开发者通过声明文件映射输入、请求、结果，不要求全部模仿现有聊天接口 |
| 组合块 | 把已有步骤封装为一个可复用步骤 | 对外暴露参数和结果，内部复用现有工作流，明确内部变量范围 |

三种均为扩展正式用途。优先用前面真实接入的视频/ASR 能力提炼接口，同时提供新 API 规则和组合块示例。第一版不要求构建扩展商店，也不以大规模重写全部内置块为前置条件。

原生适配器先通过受支持的平台模块随应用构建，外部服务通过连接配置调用。可导入的扩展包优先承载声明式 API 规则和组合流程；“导入任意原生二进制即可在 Android/iOS 执行”不在本版承诺中。需要原生能力的扩展明确标注平台和安装方式，后续再评估动态分发。

### 5.2 一份块定义贯通编辑与执行

每种块至少声明：稳定命名空间与类型 ID、块/格式版本、名称和说明、输入输出类型、默认值及必填项、可用输入场景、变量读写范围、子步骤规则、副作用、取消/错误行为、资源与能力要求。

编辑器据此提供候选和提示，校验器检查连接与作用域，执行器校验实际输入输出；复杂块仍可有专用界面和处理器。内置旧 WorkflowKind 保留兼容映射，逐步接入，避免一次修改全部序列化和队列快照。

引擎适配器还需声明模型准备、语言/设备支持、初始化、并发额度与释放方式。API 规则需声明地址/方法、JSON 或附件映射、认证引用、结果类型、JSON/完整流式条目解析、超时/重试/并发和音频时间戳能力。密钥通过用户配置的引用提供，不放入可分享的规则包。

未知块、缺失引擎或不支持的平台要在导入/执行前明确报出；保留可恢复的定义，不静默丢块或偷偷换成另一个引擎。升级有版本迁移，卸载前说明受影响的工作流。

### 5.3 工作流分类与可执行场景分开

用户按图文翻译、视频画面、音频字幕、阅读辅助、自定义查找工作流；分类可以是显示标签。实际执行另由输入场景定义系统变量、可用块和必要结构。

旧漫画流程沿用兼容规则；视频帧复用图像能力；纯字幕/音频流程不要求 SEG。允许一个流程声明多个兼容入口，但不能仅改分类就把不兼容流程标成可用。

### 5.4 遮罩扩展与开发说明

分开管理“区域是什么”和“怎样绘制”：现有气泡/游离文字语义继续有效，绘制策略可扩展。新增区域语义或结果类型时定义识别输出、坐标和兼容处理；字幕始终是独立时间轨。

开发者说明至少包含：完整目录示例、声明字段、引擎适配器接口、API 请求/返回映射、组合块参数、能力与变量规则、取消/错误、版本迁移、平台支持和调试方法。

完成标准：用一个不同请求/返回结构的 API 块证明能新增调用规则；用已接入的 ASR 等能力提供可运行的引擎适配范例；再提供一个组合块。它们均能在编辑、校验、运行、结果显示中一致工作，且有无需私人密钥的测试样例。

## 九、第六批：有无 API 都能使用的 Agent

### 6.1 无 API：通过会话管理工作流任务

首版 Agent 作为会话式任务入口。用户添加图片、PDF、ZIP 或本地视频，选择工作流与目标语言，确认输入范围后提交任务。复用现有或前面补齐的导入器和执行链，不在 Agent 内重新实现解压、分页和翻译。

**未配置聊天 API 时，这条路径必须完整可用。** 界面提供明确操作和参数，任务卡显示排队、处理、取消、重试及完成结果。任务使用本地工作流就按本地能力执行；若选中的流程含 API 块，定位到缺失配置，让用户补齐或选择兼容的本地流程，不能把整个 Agent 入口锁住。

无模型时依靠明确的任务按钮、流程选择和有限的确定性指令，不承诺任意自然语言理解。会话保存任务及成果引用，重新打开能继续查阅，不复制大型附件。输出由实际工作流决定，可为分页图像、译文、字幕或成果包；视频任务仍交付遮罩/字幕数据。

### 6.2 有 API：增加自然语言交互和工具调度

配置可用的生成式模型 API 后，增加自由对话、解释、选择合适工作流和有限工具调用。工具调用经同一能力检查与参数校验进入任务系统；运行状态、取消与结果回填复用已有机制。

文件处理、翻译、分享等实际动作有可追踪的任务记录；模型回复不能冒充已经完成的任务。支持从阅读器当前页和播放器当前时间段进入会话，结果能返回对应位置。

历史管理适配手机与宽屏。分享首版使用系统文件分享，结果卡能保存或打开实际成果；在线公开链接另立服务方案，不把它塞进静态目录分发。

### 6.3 摘要作为正式成果管理

按需生成页、章和视频时间段摘要，记录源内容、译文版本、覆盖范围及生成配置。源内容变化后标记待更新，人工修改不被后台重算覆盖；导入时不自动给所有页生成摘要。

无可用生成式模型时准确显示摘要能力状态，Agent 的工作流翻译仍可用。既有漫画简介与新生成的页/章摘要分开存放，避免污染书目元数据。

**第六批完成标准：** 删除/不配置聊天 API 后，Agent 仍能接收内容、调用本地工作流翻译、显示任务、恢复会话并保存/分享成果；配置 API 后再验收对话、工具调用与摘要。两种模式使用相同任务和成果身份。

## 十、第七批：以 iOS 为优先的跨平台实施

近期新增的数据格式使用可序列化的媒体身份、时间、坐标、流程与成果类型；文件访问、解码、图像对象、模型加载和系统分享由平台适配层负责。避免在新增公共协议中直接放 Android URI、Bitmap 或 Activity。

当前 core:model、core:workflow 等仍是 JVM 模块，并不能因为名称叫 core 就视为已跨平台。远期先清点 Java/Android 依赖，再验证少量真正能共享的类型、校验和执行逻辑。

iOS 阶段依次交付：

1. 准备 Mac、[Xcode](https://developer.apple.com/xcode/) 与测试环境，跑通文件导入和最小阅读/播放壳。
2. 在真实 iOS 编译目标验证共享模型、工作流校验、基本执行和成果读写；普通 JVM 测试不能代替这一验证。
3. 接通本地视频取帧、播放时间、遮罩和字幕，再验证一个已有翻译路线及选定 ASR。
4. 根据以上结果选择共享界面的范围，补齐权限、生命周期、存储和系统分享；其他平台随后安排。

[Kotlin Multiplatform 的平台支持](https://kotlinlang.org/docs/multiplatform/supported-platforms.html)是可选技术依据，实际方案以本应用链路验证为准。现阶段不承诺全部 Android 原生引擎无需修改即可运行于 iOS。

## 十一、三项可独立推进的配套任务

### GitHub 用户规模统计（近期必做）

目标是在 GitHub 项目页看到应用使用规模及历史变化。没有账号体系时，以安装为单位进行去重，公开展示“参与统计的累计安装数”和“最近 30 天活跃安装数”，注明覆盖范围、统计周期和更新时间；不将它宣称为精确的自然人人数。GitHub 下载次数可以额外展示，不能替代本任务。

实现采用以下链路：

1. 应用在用户启用使用统计后创建随机安装标识，升级保持不变；首次使用与按天去重的活跃事件进入低频上报队列。关闭后停止上报并清空待发统计，离线或上报失败不影响阅读和翻译。不采集硬件指纹、阅读内容、附件、译文或 API 密钥。
2. 用一个轻量接收接口和去重存储处理安装/活跃事件，优先评估免费额度方案，实施时验证费用边界和实际网络可达性。处理重试、重复事件、日期窗口、超频请求和测试流量，不为每次启动创建 GitHub Issue、Commit 或 Actions 运行。
3. GitHub Actions 定时读取汇总，写入统计专用分支或目录的 JSON 和按日历史，在 README 徽章或项目统计页展示。公开仓库只保存汇总，不公开安装标识和原始事件；统计更新不触发应用全量构建。Gitee 可镜像公开汇总。

客户端不携带仓库写入 Token；写入由服务端或 Actions 的受控凭据完成。GitHub 的[仓库文件写入接口](https://docs.github.com/en/rest/repos/contents#create-or-update-file-contents)需要相应授权；[GitHub Pages](https://docs.github.com/en/pages/getting-started-with-github-pages/what-is-github-pages)仅用于展示静态汇总。这里的服务选择是本任务的实施步骤，不再把用户统计推到未定的远期。

完成标准：两份独立安装能增加两个参与统计的安装记录，同一安装升级、重复启动和重试不会重复增加累计值；近 30 天活跃按安装去重并正确滚动。清数据或重新安装可能产生新标识，展示口径对此说明。关闭统计、离线和失败重试均不干扰核心功能；开发/测试流量不进入正式汇总；GitHub 展示与接收端汇总一致，能看到更新时间和历史变化。

### GitHub 提交和发布管道搭建、简化与优化（近期必做）

现有 [verify.yml](../../.github/workflows/verify.yml)是搭建基础，把拉取模型/源码、Debug、测试、Lint、Release 和 JNI 验证放在同一条执行链。在此基础上建立清楚的快速检查、完整验证和候选发布入口，简化普通提交操作并缩短反馈，保留正式包应有的完整验证。

- 普通提交运行与改动范围相关的检查和必要编译；文档变更不触发完整原生构建。
- 用缓存和固定版本输入减少重复下载；源码/原生/JNI 变化不能因路径筛选漏掉验证，无法确定影响时回退到完整检查。
- 主分支、候选发布或手动完整验证入口运行必要的完整构建、Lint、原生/JNI 和发布校验；触发方式实施时根据现有仓库规则收敛，避免同一提交重复打包。
- 沿用现有签名与打包流程；持续集成的未签名构建、签名候选和正式发布产物明确区分。既有证书与升级关系保持连续。
- 保存可定位的失败日志和报告。按[现有发布要求](../RELEASING.zh-CN.md)完成正式候选的实际验收，不把历史通过数量当本批结果。

完成标准：PR、主分支提交和手动入口均按预期触发；文档、普通代码、原生/JNI 三类改动有可核对的执行记录；缓存失效仍能完整运行。记录优化前后任务数、重复下载/打包情况和执行耗时，确认反馈改善且正式入口仍覆盖必要检查。未经新任务要求，本计划不自动发布 Release。

### GitHub JSON、Gitee 镜像和下载次数

静态目录先用于版本更新信息、工作流/扩展目录及公开下载数据。[GitHub Pages](https://docs.github.com/en/pages/getting-started-with-github-pages/what-is-github-pages)提供静态文件托管；也可使用实际验证过的仓库公开下载地址。实施时核对具体可用地址与额度，不预设 Gitee Pages 一定可用。

清单包含格式版本、内容版本、最低兼容版本及文件校验。镜像同步发布同一版本的内容；主源失败切镜像，两者都失败使用上次可用清单和内置默认值。清单不包含用户密钥、个人会话或翻译文件。

GitHub 下载次数由流程汇总为 JSON，标明口径及更新时间，并与上面的安装/活跃统计分开展示。目录分发、下载次数和用户规模统计分别验收，不以其中任一项代替其他事项。

完成标准：主源、镜像、离线回退和版本不匹配都有确定行为；错误清单不会让本地阅读/翻译停止。任何可执行扩展的发布与验证另按扩展协议处理，不因它出现在 JSON 里就直接执行。

## 十二、所有批次共同遵循的数据和验证规则

### 共享最小信息，不先重建整个框架

新成果至少能追溯到：源内容身份、页或时间范围、语言、工作流/相关配置、结果类型、版本和人工修改状态。任务另记录进度、取消和错误，成果只保留必要引用。视频帧、字幕与未来摘要通过这些信息关联，不需要先把所有旧表改造成一个大而全的模型。

读取旧数据保留兼容路径。变更输入场景、块类型、存储或备份格式时同时处理版本与迁移，验证旧工作流、在途任务和已有成果。正式成果与可重建缓存的边界从新增数据第一天就确定。

### 每项完成都留下可接续的记录

每个任务记录：实际改动、对应问题、必要测试/操作与结果、未验证项、数据兼容影响、当前下一项。只有达到对应完成标准才标为完成；静态推断、单测、模拟器、真机和正式包验证分别写明。

纯文档或低影响界面修改采用最小充分检查；类型/并发/存储问题补能复现差异的测试；播放、分享、文件授权和 ASR 性能按实际平台验证。已有相关检查通过后不反复无差别重跑全套，原生或发布变化仍执行必需检查。

需要 DS 协作时按本地 deepseek-coding-delegate 与 targeted-validation 技能委派有边界的实现或验证；Codex 独立复核结果。不得以另一 Codex 子代理冒充 DS，也不得把 Harness 正常退出等同于功能通过。

本计划不固定发布日期。每一批以实际完成标准和记录为准，避免在设备与 ASR 选型尚未实测时给出虚构工期。

**第一场执行对话从任务 1.1 开始，随后推进第一批；第一批不夹带完整插件平台、Agent 或 iOS 迁移。** 当前确认的输入输出阻断修完后，尽快进入第二批视频适配，其他非阻断猫爪改进可继续分批处理。

可以在新对话直接使用：

> 请读取 docs/plans/2026-10-20-final-plan.zh-CN.md、docs/plans/2026-10-20-workflow-block-audit.zh-CN.md 和 docs/plans/2026-10-20-execution-progress.zh-CN.md，按最终计划开始第一批，先处理 1.1“新增上下文输出不可选”，然后推进本批其他任务。保留当前工作区已有改动，采用最小充分验证，完成后更新执行进度，写清已完成、未验证及下一项。不要在本批改名或顺带展开完整插件平台、Agent 和 iOS 迁移。

后续对话沿用同一入口，把“第一批”替换为进度表中的下一任务。若执行中发现与静态审查不同的事实，更新证据与实施记录，在本计划边界内选择改动最小、结果正确的方案。
