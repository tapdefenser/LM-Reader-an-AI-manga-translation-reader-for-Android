## 这次已经确定的方向

**近期并列做好阅读、翻译和本地视频；新功能优先交付视频，Agent 排在后面。**

应用的主线是“导入外语内容 → 看懂内容 → 校对并保存成果 → 下次继续或分享”。阅读器、视频和未来的 Agent 共用工作流与成果管理。近期首页先方便继续阅读、继续观看和导入内容；Agent 成熟后再成为独立入口。

反复出现的深层问题是：**这些能力怎样共同交付用户能信任、能继续使用的成果？** 猫爪输入输出、上下文选不到、缓存不知道能否删除，都会让用户在流程中途停住。近期投入要同时解决这些阻碍，并用本地视频检验工作流能否扩展到新的内容。

- 视频只接入本地文件，不建设站点下载。
- 画面文字和音频字幕是两条流程，共用猫爪工作流中的识别、文本处理和翻译能力。
- 播放时显示遮罩或字幕，保留原视频；本阶段不生成、烧录或重新编码视频。
- 不集成通用大模型聊天推理引擎，不安排 llama.cpp/Gemma 下载和基准项目。没有 API 时，继续支持已有本地工作流。
- 音频识别先评估专用离线组件，其次支持能识别语音的 LLM API，同时支持导入已有字幕。专用 ASR 是独立的语音识别能力。
- 远期优先考虑 iOS，再安排其他平台；近期不迁移整个 Android 工程。
- 扩展围绕新增猫爪块、Agent 能力和可能的遮罩样式；整个应用继续围绕工作流组织。

## 视频实际怎样使用

### 看懂画面里的文字

用户打开本地视频，选择现有工作流。应用取出合适的视频帧，运行 SEG、OCR、机翻或已配置的 API，把结果覆盖在播放画面上。

图像处理步骤和现有工作流继续复用，先为视频帧补齐临时输入、时间和坐标适配。需要新做的是本地播放器、取帧、时间定位、结果保存，以及视频画面与遮罩之间的坐标对应。现有屏幕视频模式里的去重和区域匹配可以参考复用，但不能直接代替这些功能。纯字幕流程另设输入与校验规则，不要求它先执行 SEG。

先用暂停的一帧验证链路，紧接着完成连续播放、跳转和重新打开。**只翻译一张暂停画面是内部里程碑，不能算视频功能交付完成。**

### 听懂视频里的声音

音轨 → 语音识别 → 带时间的文字 → 猫爪翻译流程 → 播放器字幕。

三种输入都纳入计划：

1. **专用离线语音识别优先。** 比较现成开源组件，依据语言、识别准确度、时间戳、模型体积、运行内存和速度选型。按需安装所需模型，最终先集成一套；不同时嵌入多套运行时。
2. **支持语音识别的 LLM API。** 作为另一条可选路线，检查音频格式、时长和时间戳能力；不能把现有“能发图片”的 API 功能当成已经支持音频。
3. **已有字幕直接导入。** 优先验证 SRT，再按实际需要增加其他格式；字幕文字可以使用现有离线机翻，无需再识别语音。

没有 API 时，在本地识别/翻译模型已就绪且语言方向受支持的情况下，画面翻译可以使用已有本地路线；音频自动生成字幕还需要已安装且支持该语言的离线 ASR；导入的字幕可交给已就绪的本地翻译。应用要分别显示这些能力的准备状态。

### 气泡遮罩、画面文字与字幕分开

本稿把你写的“字母”按“字幕”理解。

- **气泡文字：** 保留气泡轮廓，在气泡内遮盖原文并显示译文。
- **游离文字及画面中已有的硬字幕：** 按所在位置处理，不强套气泡形状。
- **音频生成或文件导入的字幕：** 使用独立字幕轨，按播放时间显示，可选择原文、译文或双语。

画面遮罩和音频字幕可以分别开关。跳转、暂停、旋转或改变播放速度后，不能把旧画面的译文盖到新画面。结果保存为应用数据，下次继续使用原视频和已有翻译，不重复生成视频副本。

## 近期按这个顺序交付

### 第一轮：猫爪更可靠，阅读更顺手，视频链路开始跑通

这几项一起推进，不把视频排在通用框架之后：

- 逐块收紧输入输出、默认值和作用域规则，优先处理会影响实际结果的问题；明确重译与保留人工成果的边界。
- 把你反馈的“新增上下文无法选择输出”列为首轮问题：目前只显示当前可写的上下文变量，外层变量在异步循环内会被隐藏，也缺少解释。补齐创建引导、不可选原因，并统一编辑、校验和执行规则；不只放开一个选择器。
- 翻译设置默认只展示语言、方式和准备状态；识别、排版等高级参数分别折叠。缺包、缺配置时能直接补齐，再继续原任务。
- 阅读器增加“分享本页”和“保存本页”，支持原图与当前译文效果；保存到文件或相册。保留原图，处理未保存校对，并使用整页内容而非把工具栏一起截图。
- 做本地视频导入和播放，把选定视频帧接入现有工作流；同步评估离线语音识别。
- 先建立译文、模型、任务临时文件和普通缓存的分类清单，避免新增视频数据后无法管理。

这一轮验收看具体结果：已有漫画能正常读、译、改；本页真的能被其他应用打开；猫爪显示的输入输出与执行相符；上下文在同层、外层同步与外层异步三种用法中，有正确结果或明确指引；本地视频帧能得到正确遮罩。单帧验证之后仍要继续完成下一轮。

### 第二轮：本地视频两条翻译路线可长期使用

- 连续播放时正确显示画面遮罩，能拖动、暂停、继续、切换横竖屏，并保存翻译进度和结果。
- 离线 ASR 通过准确度、时间戳和资源评估后接入，已有字幕导入可先独立交付；语音 LLM API 随后按真实音频/时间戳能力适配。三种路线都在范围内，但不要求未经验证的组件同一天交付。
- 视频库提供继续观看、翻译状态和片单；先把常用入口放在图库下方。
- 每部漫画和视频都能看到译文及可归属的取帧、缩略图等缓存占用，可按页、章节、时间段或整部作品管理。

这一轮完成的标准是：**打开本地视频 → 翻译画面/声音 → 校对 → 退出再打开仍能继续。** 不以生成新视频作为验收条件。

### 随后：工作流分类、扩展与 Agent

按图文翻译、视频画面、音频字幕、阅读辅助、自定义来整理工作流。分类帮助查找；输入类型、可用块和校验规则另行定义，不能只改一个分类名。

扩展主要允许新增猫爪块，包括新引擎适配、新的 API 调用规则和新处理能力；封装现有流程也作为正式扩展方式。每个块声明输入、输出、默认值、可用范围和副作用；界面、校验和执行共用这份定义，避免三处各写一遍后不一致。提供可以运行的示例和开发者说明，接入边界详见最终计划。

Agent 通过相同的块和工作流执行任务，补上会话、上下文和有限的工具调用。未配置 API 时，Agent 入口仍可选择文件、目标语言和已有本地工作流，执行翻译并展示成果；需要生成式模型的对话、解释和摘要按已配置能力启用。

可扩展遮罩样式，但文字区域类型与绘制方式分开设计。音频字幕保持独立时间轨，不为了统一接口而伪装成气泡。

## 缓存、垃圾和成果怎样管理

设置中提供统一“数据与空间”入口，作品详情提供“这部作品的数据”。用户能看懂哪些可以清理、哪些是自己的成果。

作品页只统计可归属的数据。共享模型、应用级运行缓存在全局入口单列，删除某部作品不连带卸载其他作品也在使用的模型。

| 用户看到的内容 | 处理方式 |
|---|---|
| 原图、原视频、主动保存或导出的文件 | 清缓存不删除 |
| 译文、人工校对、字幕、批注 | 作为正式成果，支持备份和明确范围的删除 |
| 预览、缩略图、取帧及识别中间缓存 | 按容量清理，避开正在使用的任务 |
| 模型与任务临时文件 | 区分卸载模型、释放运行内存、清理已结束任务；保留恢复所需数据 |

有 Agent 后，页/章摘要及视频时间段摘要也由这里管理。按需生成，记录它基于哪些页、哪版译文及什么时间范围；原文或译文变化后标记待更新。人工修改不会被后台重算覆盖，不在导入时强制给每页生成摘要。

沿用已经存在的译文持久化、页级复用、导出恢复和备份回滚。新做管理入口和缺少的规则，不把这些基础全部推倒重做。

## GitHub JSON、Gitee 镜像与发布

先采用**只读文件分发**：GitHub 发布更新信息、工作流目录、扩展目录等 JSON，Gitee 提供相同版本的镜像。主地址失败后切换镜像，再失败则使用上次可用数据和内置默认值；离线使用不因此受阻。这符合 [GitHub Pages 的静态托管方式](https://docs.github.com/en/pages/getting-started-with-github-pages/what-is-github-pages)，实际部署仍需核对[使用限制](https://docs.github.com/en/pages/getting-started-with-github-pages/github-pages-limits)。

两个来源携带相同的版本和校验信息，避免混装不同版本。实施时验证具体公开下载地址和镜像同步方式，不假定同步是即时的，也不保证无额度限制。

这条路线暂不承担用户文件托管、在线对话、在线分享链接或客户端写入用户计数。若展示 GitHub 下载量，可以由发布流程生成汇总 JSON，明确标成下载次数。

提交与发布管道仍需简化：快速检查与完整正式包检查分层，沿用原签名和现有校验。它可以与近期功能独立推进。

取消上一稿“Windows 先行”的默认安排。近期先把 Android 上的阅读与本地视频做稳；新增猫爪类型、字幕时间数据和成果格式尽量不绑定 Android 的文件 URI、界面或图像对象。
